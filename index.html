BREAKING: Preinstalled Intel driver silently breaks IPv6, knocking OneNote and Microsoft 365 offline

Intel Connectivity Performance Suite rewrites the IPv6 Flow Label to zero partway through every TCP connection. Microsoft's edge routes on that label, so the rest of each connection lands on a server that never saw it start, and gets reset. OneNote stopped syncing for nearly three weeks, and the cause was nowhere a normal user or support desk would look.

Affected? Check in one command

In PowerShell: 1..10 | % { curl.exe -6 -sS -o NUL -w "%{http_code}`n" https://api.onedrive.com/ }. Any "Connection was reset" lines, on a PC with Intel Connectivity Performance Suite, point to this bug. Check, fix and undo instructions.

What is going on

The driver is IntcCo11X64.sys 11.5.11.19, the "Intel Connectivity Traffic Control Callout Driver" (service INTCCoSvc, WFP provider "Rivet Networks, LLC - RFE version 6.1.0.1"). It ships as part of Intel Connectivity Performance Suite 40.25.926.0, preinstalled on the affected Samsung Galaxy Book. The Windows stack sends the SYN with a proper IPv6 Flow Label. The Intel callout then re-emits every ACK and data segment with the label set to 0.

RFC 6437 expects the label to stay constant for the life of a flow. Microsoft's Azure Front Door hashes on it, so the label-0 packets go to a different node, which answers with a reset. The SYN-ACK comes back at hop limit 47 and the RST at hop limit 49, so two different machines are answering. IPv4 has no flow label and is unaffected. That is why OneNote on the web and on a phone kept working and nobody could explain the failure. Full wire evidence and A/B table.

Three companies, three failures

Intel

Ships a kernel driver that breaks a basic IPv6 rule on every connection. It reports nothing, so the owner can't see it.

Samsung

Preinstalled it. The owner never chose it, and none of Samsung's tools detect or mention it.

Microsoft

Its edge falls over on it, where Google, Cloudflare and Akamai don't. OneNote then shows a dead connection as "Up to date". An escalated support case opened in August never found the cause.

How it was found

Sign-out, cache resets, Office repair and reinstalling are all irrelevant to this defect, and none of them could have found it. An OpenAI Codex session gave up on it. Anthropic's Claude, running as an agent on the affected machine, then found it in a few hours. It timed the resets against the round trip, captured traffic below every filter driver and decoded the IPv6 headers. It inventoried every Windows Filtering Platform callout and disabled network filter drivers one at a time, reversibly, until only the Intel driver was left.
